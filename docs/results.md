# 实测报告 · 2026-10-05

本次发布验证的是个人日程工具：能否排下事情、临时有事时要改几件、排不下时能否解释，
以及从输入到日历文件的流程是否可用。算法采用现有 OR-Tools CP-SAT；本报告不主张新求解理论。

同一冻结版本在 macOS ARM64 和 Linux x86_64 上各运行 210 个公开排程案例。
可选文本整理在一张 RTX 5090 上实际运行 Qwen3-4B-Instruct-2507。
全部输入、各方法输出、失败结果、计时和模型原文都保留在
[原始记录目录](results/2026-10-05/)。未使用个人真实日历或待办。

## 方法与可复现边界

排程案例由 `benchmarks/fixtures.py` 生成，固定种子 `20261005`：

- 48 个由可行安排反向构造的案例，包含开始限制、截止时间、拆分、依赖和预约。
  构造出来的已知安排只用于检查，不提供给任何排程方法。
- 96 个微型案例，每例 3 件事、12 分钟。独立的直接枚举器逐分钟枚举可能安排，
  比较可行性、保留重要度、改动事项数和开始偏移；枚举器不调用 CP-SAT 或生产检查器。
- 32 个时间宽松的重排案例。一个新预约占用一件旧任务；已知只需改一件。
- 32 个期限受限的重排案例。新预约迫使被占用任务挪到相邻旧任务的位置；已知至少改两件。
- 两个可读示例：开始限制导致简单插入错失可行方案，以及必做时长超出空闲容量。

这些生成方式会影响难度分布。测试说明这份公开案例集上的行为，不能等同真实人群日程的分布，
也不是与所有排程产品的比较。作者使用同一批案例开发检查器和排程实现，没有独立隐藏测试集。

四个启发式对照方法也由本项目实现，使用相同输入和独立检查器：

| 方法名 | 做法 |
| --- | --- |
| `earliest_deadline` | 先安排前置任务，再按截止时间顺序找第一个能放下的时段 |
| `priority_first` | 先安排前置任务，再按重要度顺序插入 |
| `preserve_then_edf` | 先保留能保留的旧位置，再按截止时间插入剩余事项 |
| `preserve_or_rebuild` | 先尝试保留；若保留阻止完成，则全部按截止时间重建 |
| `dayweave` | 按约束求解，依次优化重要度、改动数、偏移和完成时间 |

四个对照方法较快，但不回溯穷举所有组合。比较用来展示组合约束和稳定重排的作用，
没有把这些基线描述成商业产品、其他 agent 项目或同等最优求解器。
排程限时 3 秒、单 worker。只有四阶段全部证明最优才记为 `proven_all_objectives`。

## 排得下与排不下

macOS 和 Linux 的可行性、目标值与下列计数一致；求解耗时不同。

| 案例组 | 例数 | DayWeave 完整可行 | 截止时间插入 | 重要度插入 | 保留后插入 | 保留或重建 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 反向构造的可行案例 | 48 | 48 | 34 | 3 | 34 | 34 |
| 微型枚举案例 | 96 | 79 | 79 | 74 | 74 | 79 |
| 宽松重排 | 32 | 32 | 32 | 32 | 32 | 32 |
| 期限受限重排 | 32 | 32 | 32 | 22 | 0 | 32 |
| 两个可读示例 | 2 | 1 | 0 | 0 | 0 | 0 |

微型组有 79 例真正可行、17 例不可行，**96/96 与独立枚举一致**；
79 个可行案例的前三阶段最优目标也逐例一致。
17 个不可行案例的冲突组经过独立枚举检查：组本身不可行，删掉组内任一约束后可行。
这是集合意义上的不可再删减，不代表所有冲突组中成员数量最少。

超载示例只有 180 分钟空闲，三件必做事项总计 240 分钟。程序证明原问题不可行，
计算缺口 60 分钟，再给出允许推迟的候选安排。候选安排需要用户明确采用；
它不改变“原来的必做清单不可行”这一结果。

## 临时有事时改多少

改动数统计已有计划中开始位置或拆分发生变化的任务；旧任务被推迟也算改动。
新任务和已经移除的任务另计。仅在双方完整可行的同一组输入上比较平均值。

| 案例组与对照 | 同时完整可行的例数 | DayWeave 平均改动 | 对照平均改动 |
| --- | ---: | ---: | ---: |
| 宽松重排 vs 截止时间插入 | 32 | 1 | 8.875 |
| 宽松重排 vs 保留或重建 | 32 | 1 | 1 |
| 期限受限重排 vs 截止时间插入 | 32 | 2 | 9.125 |
| 期限受限重排 vs 重要度插入 | 22 | 2 | 9.273 |
| 期限受限重排 vs 保留或重建 | 32 | 2 | 9.125 |

时间宽松时，保留旧位置的启发式已经足够好；DayWeave 在这里没有改动数优势。
期限受限时，单纯保留会把安排卡住，全部重建又会改动较多事项。
DayWeave 在这 32 例上保留完整可行性，同时达到已知最少改动数 2。
两组共 64 例均达到各自的已知下界。不能将它换算成已经测得的人类生产力提升。

## 求解耗时

以下为单次算法调用的墙钟时间，包含该调用的求解与检查，
不包含安装、程序启动、浏览器渲染或外部网络传输。没有做统计置信区间或多次负载测量。

| DayWeave 案例组 | macOS 中位数 / P95，毫秒 | Linux 中位数 / P95，毫秒 |
| --- | ---: | ---: |
| 构造可行案例 | 3.587 / 6.717 | 12.747 / 24.485 |
| 微型枚举案例 | 2.412 / 4.517 | 9.564 / 18.048 |
| 宽松重排 | 9.119 / 9.843 | 35.669 / 35.963 |
| 期限受限重排 | 8.520 / 9.603 | 17.950 / 34.727 |

例如 Linux 期限受限组中，保留或重建基线的中位数是 0.311 毫秒；
DayWeave 的收益是少改事情和组合搜索，付出的代价是更多计算。
本组所有可行输出都完成四阶段最优证明；更大或更紧的输入可能仅得到可行解，
或在限时内不能确定可行性。界面和 JSON 会显示实际证明状态。

## RTX 5090 的实际文本整理

测试模型是 [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)，
固定 revision `cdbee75f17c01a7cc42f958dc650907174af0554`。
10 个用于推理的配置、tokenizer 和 safetensors 文件重新计算内容哈希，
与官方固定 revision 的文件清单逐项一致，见 [模型验证记录](results/2026-10-05/model-manifest.json)。
模型文件不随本项目分发。

在一张 NVIDIA GeForce RTX 5090 上用 BF16、SDPA、贪心生成、最多 640 个新 token 运行。
GPU 总显存 32607 MiB，服务运行时占用 8389 MiB；PyTorch 2.8.0、CUDA 12.8、
Transformers 4.57.6。排程始终在 CPU 上运行。其他环境信息见
[Linux 环境记录](results/2026-10-05/linux-environment.json)。

公开的 18 条笔记是 9 组事项各写成竖线格式和自由段落，共 54 个标注任务。
它们是开发用模板案例，且曾用于修改 prompt、日期解析和回退处理，**不是留出集准确率测试**。
匹配标题必须对应且只对应一个标注事项，时长和期限都正确才记整项正确；缺失任务保留在分母。
原文没有的字段应保持空值。报告同时记录错误、多余项和失败后的回退内容。

| 输入方式 | 不接模型 | 配置本地模型 |
| --- | ---: | ---: |
| 9 条竖线格式，27 件事全部字段正确 | 27 / 27 | 27 / 27，规则直接处理，未调用模型 |
| 9 条自由段落，27 件事全部字段正确 | 0 / 27 | 24 / 27 |
| 自由段落直接接受模型结果 | 无 | 8 / 9 条 |
| 模型结果被拒绝并显式回退 | 无 | 1 / 9 条 |

自由段落共返回 25 项，24 项对应正确任务，1 项是失败后回退的未拆开段落。
固定记录中 `capture-00-prose` 的模型输出是损坏的 JSON，缺失最后一项的键值结构；
系统拒绝该输出并展示回退，没有计成“成功解析”。这条笔记的三件任务都没有通过匹配。
模型原文和错误理由见 [逐条记录](results/2026-10-05/model-capture-results.jsonl)。

自由段落的单条整理中位耗时为 1207.536 毫秒，包含本机 HTTP 调用与推理。
规则格式与自由段落合计是 51/54 整项正确；不以这个混合比例掩盖规则处理和模型处理的区别。
16 个标注缺失字段中，在成功匹配的输出上没有观察到补造字段；
未匹配项不参与这个字段指标，不能据此宣称模型永不编造。
离线解析采用一行一件事，整段自由文字失败的 0/27 也完整保留。
普通用户用核心工具不需要安装或运行模型。

## 实际浏览器流程

验收采用真实服务和公开示例数据，截图由浏览器生成：

- 完整安排 8 件事、630 分钟；固定简历事项后仍保持原位置。
- 插入一个 10:00–10:45 预约后，只调整申请材料事项，其余原开始时间保持。
- 超载时显示 60 分钟缺口，导出保持不可用；明确允许推迟后得到可复核的两件事日程。
- 真实下载的 `.ics` 用日历解析器读回，恰好两条任务事件，没有复制已有预约。
- 新建个人计划按当前时间安排；粘贴内容缺少时长时填入 45 分钟，最后一个仍有焦点的字段也能保存。
- 导入每日重复课程并排除一次，实际生成两次课程；晚间课程在视图中可见。
- 真实下载 JSON 备份，再通过文件选择恢复；恢复后需重新计算才可导出。
- 在 375×812 和 1280 像素宽度下检查：页面本身不水平溢出，窄屏日历在自身区域内滚动。

## 安装与工程验收

macOS 和服务器均通过 35 个测试；本机同时通过 Ruff 检查、Python 格式检查和严格类型检查。
测试覆盖独立枚举、最少改动、不可行冲突组、拆分完整性、固定安排、依赖、时区、日历往返、

已安装包的 19 个运行代码、类型声明和界面文件逐字节匹配发布源文件。
源码启动器也在独立解压目录中完成首次创建环境、从 PyPI 安装依赖和提供真实 HTTP 界面。
